# ADR 0001: Source classification inheritance for derived data flows

- Status: Accepted for implementation after maintainer review on 2026-11-19
- Date: 2026-11-19
- Scope: `data_flow.observed` contract and Python/TypeScript reference SDKs

## Context

An agent may derive a summary, extract, aggregate, or memory from multiple inputs. The classifier that observes the resulting value may assign a less restrictive label than one or more contributing sources. Recording only that output label loses the source-side classification context and can make the derived event appear less restricted than its inputs.

The SDK does not own customer data stores or DLP policy. It cannot safely fetch or reclassify source content, and model-authored labels are not an acceptable trust source.

## Decision

Accept already-computed source classification metadata from the caller. The caller is responsible for obtaining it from a trusted upstream DLP classifier, policy engine, or label store and for supplying the complete set of contributing sources.

For a single explicitly declared total order within one taxonomy, compute:

`effective = max(observed_output, source_1, ..., source_n)`

The order is supplied as least-to-most restrictive labels; labels are never compared lexically and no universal hierarchy is inferred.

The optional event fields are:

- `observed_classification`: the output classifier's result before inheritance;
- `source_classifications`: one source endpoint and its classification metadata for every supplied contributing source;
- `classification`: the effective result after applying the explicit order.

The two lineage fields must appear together. Existing direct data-flow calls remain unchanged when neither is supplied. The implementation bounds lineage to 1,024 sources and rejects empty lineage, duplicate endpoint references, unknown labels, mixed taxonomies, and missing or mismatched ordering input. Events carry references and labels only, never source content.

## Trust and security boundaries

This mechanism propagates caller-supplied labels; it does not authenticate them, prove lineage completeness, or make an incorrect source label correct. Integrators must not pass model-authored labels without trusted validation.

It does not implement declassification, reclassification, revocation propagation, or authorization. Those controls remain with the policy and data-governance systems that own the source data.

Endpoint identifiers remain metadata and may still be sensitive. Integrators must pseudonymize them according to the existing data-flow classification guidance.

## Alternatives considered

1. **Classify source values inside the SDK.** Rejected because the SDK does not own source data access or a trusted policy engine. It would expand data exposure and couple the telemetry SDK to adopter-specific DLP systems.
2. **Trust labels generated by the model or transformation.** Rejected because model-authored labels are not an authoritative source of policy metadata.
3. **Derive order from label strings.** Rejected because lexical order is not a classification policy and differs across taxonomies.
4. **Emit only the effective label.** Rejected because it hides the output classifier's observation and source lineage, weakening auditability.

## Compatibility and versioning

The contract version advances from `0.1.0-alpha.6` to `0.2.0-alpha.1`, with matching Python and TypeScript package versions. The two lineage fields remain optional as a pair, so producers that omit them retain the previous event shape.

The schemas are closed to unknown properties. A consumer pinned to a pre-0.2 schema will reject an event containing the new fields even though they are optional at the producer. Consumers must update their schema copy to 0.2 before processing opted-in derived-flow events. This is an explicit pre-1.0 compatibility change and is called out in the Unreleased changelog.

## Consequences

- Adopters retain responsibility for source-label provenance and complete lineage.
- The source and output classifications become auditable without retaining raw data.
- The same explicit taxonomy order is required in both SDKs.
- Consumers pinned to pre-0.2 closed schemas must update their schema copy before processing events that opt into source-label inheritance.
- A future declassification or retroactive reclassification design must be handled separately.
